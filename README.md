微服务注册发现实战：Nacos/Eureka 服务注册中心搭建与原理剖析
微服务架构里，服务实例的IP和端口是动态变化的，调用方不能把地址写死。注册中心就是解决“谁在哪”的基础设施：服务启动时登记自己，调用方按名字查地址，实例下线时自动摘除。Nacos和Eureka是两条主流路线，理解它们的原理差异，比会敲几个配置命令重要得多。

一、注册发现的核心模型：先想清楚四件事

任何注册中心都绕不开四个动作。第一是服务注册：实例启动后把自己的服务名、IP、端口、元数据（版本、机房、权重）写入注册中心。第二是健康检查：注册中心通过心跳或主动探测判断实例是否存活，不健康的实例不能继续被调用。第三是服务发现：调用方按服务名拉取实例列表，并在本地缓存。第四是变更通知：实例上下线时，注册中心要把变化推给订阅方，或者由订阅方定时拉取。

这四个动作决定了两个关键设计：一致性模型和健康检查机制。前者影响可用性和数据准确性，后者影响故障发现的快慢。Nacos和Eureka的分野主要在这里。

二、Eureka：AP优先的“够用就好”

Eureka的设计哲学是可用性优先。它采用去中心化的对等集群，节点之间互相复制注册信息，没有主节点。写操作在任意节点接受，异步复制到其他节点，因此短时间内不同节点看到的数据可能不一致，但集群不会因为某个节点故障而整体不可写。

健康检查靠客户端心跳：实例默认每30秒续约一次，注册中心90秒没收到续约就把实例标记为不健康，再过一段时间才真正剔除。这个设计的代价是故障发现偏慢，一个实例宕机后，调用方可能在一两分钟内还能拉到它。Eureka的保护机制也值得注意：当短时间内大量心跳丢失时，它倾向于认为“是网络问题而不是实例真挂了”，暂停剔除实例，避免雪崩式误删。这个机制在真实故障时保护了注册表，但也意味着故障实例可能多存活一段时间。

Eureka的消费端是拉模式：客户端定时拉取全量注册表缓存在本地，配合Ribbon做客户端负载均衡。拉模式实现简单、注册中心压力小，但变更感知有延迟。总体看，Eureka适合对一致性要求不极端、追求简单稳定的场景，社区活跃度近年下降明显。

三、Nacos：AP/CP可切换的“双模选手”

Nacos把一致性和健康检查都做成了可配置项，这是它和Eureka最大的区别。它支持两种模式：临时实例用AP模式，基于自研的Distro协议做异步复制，靠客户端心跳保活，适合无状态服务；持久化实例用CP模式，基于Raft协议保证强一致，靠服务端主动探测健康状态，适合数据库代理这类不能误判的场景。

健康检查上，Nacos区分客户端心跳和服务端探测。临时实例走心跳，持久化实例由服务端定时发TCP/HTTP探测。探测失败的实例会被标记不健康，订阅方收到推送后更新本地列表。Nacos的推送是长连接加UDP通知，比纯拉模式感知更快，同时保留了拉模式兜底。

服务发现之外，Nacos还内置了配置中心，注册与配置共用一套集群和权限体系，减少了运维组件数量。命名空间和分组机制让多环境、多租户隔离变得简单，这是Eureka需要额外搭一套才能做到的。

四、搭建与选型的实战要点

搭建层面，无论选哪个，几个坑是共通的。集群部署至少三节点，避免单点；节点间网络要低延迟，否则心跳和复制都会抖；注册中心本身要独立于业务集群，别和业务抢资源。Nacos集群依赖外部数据库（MySQL）存持久化数据，数据库的高可用要提前规划；Eureka集群靠互相注册组成对等网，配置里要写全其他节点地址。

客户端配置上，超时和重试参数要匹配业务容忍度。心跳间隔太短增加注册中心压力，太长故障发现慢；拉取间隔决定变更感知延迟。服务优雅下线必须做：先摘流量、等在途请求处理完、再注销实例，否则调用方会打到正在关闭的实例上。注册中心要开鉴权，防止恶意注册和拉取。

选型上给一个实用判断：技术栈偏Spring Cloud Netflix、追求简单稳定、能接受分钟级故障发现，Eureka够用；需要强一致场景、想要注册配置一体化、需要多环境隔离和更快的变更推送，选Nacos。新项目目前更推荐Nacos，生态和维护更活跃。但无论选哪个，都要在调用方做本地缓存加容错，注册中心不可用时降级到缓存列表，这是注册发现架构的最后一道保险。

注册发现的本质是把“地址管理”从代码里抽出来集中治理。理解AP/CP取舍、心跳与探测的差异、推拉模式的权衡，搭建时才知道每个参数在调什么，排障时才知道该看哪一层。
